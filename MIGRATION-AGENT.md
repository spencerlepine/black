## 1. Goal and locked decisions

**Goal:** a standalone, from-scratch Rust rewrite of Pokémon Black (NDS) that runs natively and
in the browser (WebAssembly), with its own copy of all assets. No `.nds` file and no emulator at
runtime.

| #   | Decision                                                                                                                                                                                                                                           | Why                                                                                                                                                                                                                                                                                                                       |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **Rust + Bevy**, targets `x86_64` native and `wasm32-unknown-unknown` (WebGL2; WebGPU optional).                                                                                                                                                   | Bevy runs in browsers; a 2×256×192 game is far inside its performance budget. Bevy's ECS perf trap (pushing every entity and per-frame query through the system graph; escape = keep `bevy_ecs`, swap the renderer/app shell) only bites with huge entity counts; keep heavy logic in plain Rust, not per-entity systems. |
| D2  | **Game logic = faithful port.** Each ported function behaves identically to the original for all valid inputs (integer widths, wrapping, signedness, RNG call order). Verified against the original machine code.                                  | Mechanics must match the original.                                                                                                                                                                                                                                                                                        |
| D3  | **UI/graphics/sound = rewrite, not port.** Each screen is rebuilt directly in Bevy, using the original asm only as the behaviour/layout/timing spec. Do **not** emulate DS hardware (2D engines, 3D GPU, SPU) or port NitroSDK G2/G3/GX/SND calls. | The original UI drives DS hardware registers; porting it line-by-line means writing an emulator core.                                                                                                                                                                                                                     |
| D4  | **Own copy of assets.** A one-time, native-only extractor converts ROM data to standard formats in `black-rust/assets/` (PNG, OGG, JSON/RON). The game loads only those.                                                                           | Standalone; Bevy loads PNG/OGG natively; binary DS-format parsers never ship to wasm.                                                                                                                                                                                                                                     |
| D5  | **`assets/` is gitignored and private.** Regenerate with `black extract-assets`. Never commit it, never deploy the wasm build to a public URL.                                                                                                     | Nintendo IP; keep it local / access-controlled.                                                                                                                                                                                                                                                                           |
| D6  | **Logic crates are engine-agnostic** (no Bevy dependency). Only `black-game` (the app) depends on Bevy.                                                                                                                                            | Testable logic; can drop Bevy's renderer later and keep `bevy_ecs` if needed.                                                                                                                                                                                                                                             |
| D7  | **Battle UI talks to battle logic only through the server→client command stream** (`btl_adapter`/`btl_client` seam).                                                                                                                               | It's the original architecture and a clean boundary between logic and view.                                                                                                                                                                                                                                               |
| D8  | **Music: render sequenced music (SSEQ) to OGG offline first** (A9). | D9  | **Out of scope** unless re-decided: networking, Wi-Fi, C-Gear, IR, Dream World, Battle Subway online, Musicals, PWT, Pokémon Global Link, mystery gift (≈10k functions in `networking / C-Gear`).                                                  | Not needed for single-player; huge.                                                                                                                                                                                                                                                                                       |

## 3b. Reverse-engineering workflow: compute first, LLM last

**Principle:** tools do every step that can be computed (disassembly, decompilation, typing,
call graph, clustering, table extraction, harness setup, verification). The LLM does only the
semantic step that can't: turning one typed pseudo-C function into idiomatic Rust, and fixing
it when the differential test says it's wrong. The LLM should never read a raw `.s` file when
pseudo-C exists, and never more than one work packet at a time.

### Why the tools failed before (fixed 2026-10-11)

1. `main.elf` has all 182k decomp symbols (incl. ARM `$a`/`$t`/`$d` mapping symbols) but **zero-length sections**; the bytes exist only in `main.sbin` / `OVY_<n>.sbin`. Nothing could decompile it.
2. The decomp marks every `.byte`-encoded code block as `$d` (data), so the event handlers were invisible: Ghidra found **61 of 800** pool handlers in overlay 93.
3. rea needed Ghidra + JDK 21, which weren't installed.

`tools/re/mkelf.py` fixes 1 and 2: it writes a real ARM ELF (bytes + symbols) for one
co-resident overlay set, drops the `_@DummyFn`/`$b`/`$m` noise symbols, types every label that has a
mapping symbol as a function (Thumb bit set for `$t`), and seeds a `$t` + `sub_<addr>` function at
every odd word that points into loaded code (handler pools, callbacks). Result: **800/800** pool
handlers found. Ghidra, rizin, and rea all read this ELF with no extra config.

### Pipeline

| tier | step                                                                                                                                     | tool                                                                            | cost                                                                                 | output                                                                      |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 0    | Build ELF for an overlay set                                                                                                             | `mkelf.py`                                                                      | <1 s                                                                                 | `$RE_OUT/<set>/<set>.elf`                                                   |

## 5. Session protocol (coordinator + workers)

**Status markers** (first token of every checklist line):
`[ ]` todo · `[~]` in progress — append `(branch, YYYY-MM-DD)` · `[x]` done — append `(commit sha)` · `[!]` blocked — append reason · `[-]` dropped/out of scope.

**Parallel labels:**

- **PAR** — independent; can run at the same time as any other PAR item whose deps are met. Owns its own files (its own module/folder); does not edit shared types, `Cargo.toml`, or files owned by another item.
- **SEQ** — run alone in its area, by the coordinator or a single agent. Usually: defines shared types/traits other items build on, scaffolds crates, integrates many pieces, or makes an architecture decision.
- **PAR×N** — the item is a batch template; split into N parallel jobs (each job is its own sub-line under it when started).

**Rules:**

1. **Only the coordinator edits this file.** Workers report back; the coordinator ticks items. (Avoids merge conflicts on the checklist.)
2. Mark `[~]` **before** starting, so a crash/shutdown is recoverable.
3. On resume, every `[~]` item is reconciled first: branch merged → `[x]`; branch has partial work → hand back to a worker; nothing there → `[ ]`.
4. **Agent-tool worktrees are created from `origin/main`, not local `main` (found 2026-10-12: several workers started without unpushed merges). Push verified `main` before spawning dependent workers.** **Trap (found 2026-10-13): an Agent-tool worktree with no changes is auto-removed when the worker stops; a worker resumed with SendMessage then silently works in the main checkout. Before resuming a worker that stopped with nothing staged, create a worktree yourself (`git worktree add /tmp/blk/wt-<ID> -b <id> main`) and tell it that path; check `git status` on main after every worker report.** Workers run in their own git worktree (Agent tool, `subagent_type: "general-purpose"`, `isolation: "worktree"`; the Agent tool picks the branch name, use it as-is). The worktree is a checkout of the whole `black` repo: the worker's files are under `<worktree>/black-rust/`. Workers edit and **stage** there only; they never commit (see "Commits").
5. Worker done = changes staged, `tools/gate.sh` green in the worktree; report (format below).
6. Merge (coordinator): review `git -C <worktree> diff --cached --stat`, reject per "Model routing" rule 2, commit in the worktree (`git -C <worktree> commit -m "<ID>: <one line> (XX% complete)"`, see "Commits"), `git -C <worktree> rebase main`, then from `$HOME/workplace/black`: `git merge --ff-only <branch>` and `git push origin main`. If the rebase conflicts outside this file, hand it back to the worker (SendMessage) or redo the item. Re-run the gate **and the item's `tools/rom-diff` / `check-*.sh` check** on merged `main` after every merge batch (the gate runs `sync-docs.py`, which rewrites SYMBOLS.md/checklists without failing: commit what it changes); **after merging any port, run `python3 tools/check-force.py` (exit 1 = another area's spec still stubs a now-PORTED fn without `force`; `--fix` adds it, force-only) — found 2026-10-13: B11a's force edits predated B13-spec2's new client specs, leaving 118 unforced lines;** a hash that doesn't reproduce = revert the merge commit range (`git revert`, push) and re-queue the item. **After the push, launch the validator on the batch (§5b) if none is running.**
7. **Concurrency cap: 5 workers** (human, 2026-10-12, after the disk/usage issues at 8) (not hook-enforced here; you enforce it). Run them in the background and keep doing SEQ work while they run. The validator (§5b) occupies one of the 5 slots while it runs; at most one validator at a time.
8. New crates are created only by SEQ item Z2 (scaffolding), never by PAR workers, to avoid `Cargo.lock` / shared-type races.
9. Never edit `black-rom/`. Never commit `assets/`, ROM bytes, or extracted dumps (`/tmp/blk/re/**` included).
10. **Disk (2026-10-12 macOS, 2026-10-13 Linux): a Bevy-including target dir is ~10–14 GB; the macOS data volume filled up with 8 per-worker targets, and on the Linux host one full-gate target alone filled the 16 GB `/tmp` tmpfs.** ~~Shared target dir~~ **UNSAFE (found 2026-10-12): cargo artifacts of the same crates from different worktrees collide, so a check can run another worktree's code.** Each worker uses its own `CARGO_TARGET_DIR=/tmp/blk/target-<ID>` + `BLK_OUT=/tmp/blk/out-<ID>` (check-script outputs) + `GATE_NO_GAME=1 tools/gate.sh` (skips Bevy/black-game, ~1–2 GB per worker); the coordinator runs the full gate + all checks on merged main in `/tmp/blk/target-coord`. Check `df -h /tmp /` each iteration; below ~10 GB free, delete finished workers' targets and don't spawn. Previously: each worker writes test logs to a unique path (gate writes `$CARGO_TARGET_DIR/gate-test.log`) and uses `CARGO_TARGET_DIR=/tmp/blk/target-<item-id>`. Delete that target dir after the merge (disk).
11. **Shared tool files are coordinator-owned:** `tools/re/signatures.tsv`, `tools/re/sets.txt`, this file. Workers put new prototypes/sets in their report; the coordinator appends them, commits, and re-runs `REUSE=1 decompile.sh`.
12. `decompile.sh` writes to `/tmp/blk/re/<set>/`; only the coordinator runs it (no concurrent runs of the same set). Workers only read `pc/`, and may run rizin/rea read-only.

**Failure policy (never stall):**

- Worker fails or returns without a green gate: retry with the failure output in the prompt, escalating the model per "Model routing" rule 1. Final failure: mark the item `[!] <reason>` (or split it into smaller jobs and retry those), add the question to §8, move on.
- Unverifiable behaviour inside an item: port what verifies, stub the rest behind a trait with `// UNVERIFIED:`, add to §8, and finish the item. Don't block on it.
- `main` gate red: fixing it comes before any new work.
- Anything that needs a human (by-ear audio check, visual sign-off, play-test, a decision without a default): add a line to §10, finish everything else around it, and keep going. Mark the item `[x]` with "pending sign-off" if its code is done.
- Never disable tests/lints, never weaken a differential test to make it pass.

**Usage cap (guardrail + self-recovery; human request 2026-10-12).** The plan's usage limits are global to the human's account: a rolling 5-hour session limit and a weekly limit. If a limit runs out mid-wave, every in-flight agent dies at once, leaving half-done worktrees and `[~]` lines nobody can explain. So the coordinator watches usage, stops before the limit, leaves the repo clean, and wakes itself up after the reset.

- **Reading usage.** Spawn the `usage-cap-watchdog` agent (`.claude/agents/usage-cap-watchdog.md`; Haiku, ~10 s, foreground, not a worker so it doesn't count toward the cap): `Agent({subagent_type: "usage-cap-watchdog", description: "usage check", prompt: "Report current plan usage. Run exactly: bash $HOME/workplace/black/.claude/scripts/usage-cap.sh"})`. The script path is hard-coded (absolute) in the agent file and the prompt, because agents start in the spirited repo root where `.claude/scripts/` does not exist. It returns one line: `USAGE: <GREEN|ORANGE|RED|UNKNOWN> <worst %> — <each window: %, reset time in Z, time left> [| resume_at <Z> (in …) resume_cron "<M H DoM Mon *>"]`. GREEN <75%, ORANGE 75–89%, RED ≥90% (worst of the windows). `resume_at` is the latest reset among windows at ≥75%, plus a 5-minute buffer, in UTC. `resume_cron` is the same moment in local time, ready for `CronCreate` (which reads cron specs as local time). **Copy `resume_cron` verbatim; never convert time zones yourself.** Never call the usage endpoint yourself and never read the OAuth token.
- **When it runs.** (a) At the start of every iteration (step 0). (b) Every 20 minutes from a session-only recurring cron. Its prompt starts with `USAGE-CHECK`: `CronCreate({cron: "7,27,47 * * * *", recurring: true, prompt: "USAGE-CHECK: run the usage check in MIGRATION-AGENT.md §5 \"Usage cap\" and apply the result. Do not start an iteration or call ScheduleWakeup from this turn unless you are pausing."})`. Step 0 makes sure exactly one such job exists (`CronList`). Recurring jobs auto-expire after 7 days, so recreate it when it's missing. A `USAGE-CHECK` turn only applies the mode below and ends; the loop's pending wakeup still stands.
- **Mode = the latest reading.** Record it in §2 `Usage guard` (one line, overwritten each time the mode changes):

| Reading                 | Mode            | What the coordinator does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GREEN                   | **RUN**         | Normal iteration. If §2 said DRAINING/PAUSED, the limit has recovered: set RUN, note it in §9, and continue.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ORANGE                  | **DRAIN**       | Start nothing new: no worker spawns, no new SEQ item, no retries/escalations. Running workers may finish. Merge each finished one normally (review, commit, rebase, ff-merge, gate + checks on `main`, push), since that's cheap and banks the work. Once no workers are running, **pause**.                                                                                                                                                                                                                                                                                                                              |
| RED (incl. `LIMIT HIT`) | **WRAP UP NOW** | Start nothing. Merge any worker that has already reported done and whose merge is quick. `TaskStop` every other running worker. Leave its worktree and staged changes alone (never discard) and rewrite its line as `[~] (branch, date) — paused at usage cap; partial work staged in <worktree path>`, so rule 3 hands it back on resume. Then **pause**. If something mid-merge can't finish cleanly (rebase conflict, red gate on `main`), abort it (`git rebase --abort`, or `git revert` + push for a merged range) and put the item back to `[~]`/`[ ]` with a note. `main` must be green and pushed when you stop. |
| UNKNOWN                 | (unchanged)     | Keep the current mode, but spawn no new workers until a reading succeeds. 3 UNKNOWN readings in a row → treat as ORANGE and add a §10 line with the error.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

- **Pause** (in this order; the goal is that a cold resume can explain everything from this file and git alone):
  1. Checkpoint (iteration step 4): every `[~]` line says where its partial work is, §2 and §9 are current, commit + `git push origin main`. `git status` on `main` shows nothing staged and no in-progress merge or rebase.
  2. `CronList`, then `CronDelete` the `USAGE-CHECK` job and any older resume job (a paused session must not wake every 20 minutes).
  3. Schedule the resume as a one-shot cron at `resume_cron`: `CronCreate({cron: "<resume_cron, verbatim>", recurring: false, prompt: "<the §0 /loop prompt, verbatim>"})`. If the reading had `resume_at unknown`, use 60 minutes from now: `date -d '+60 min' '+%-M %-H %-d %-m *'`.
  4. Set §2 `Usage guard` to `PAUSED (<ORANGE|RED> <n>%) until <resume_at>Z — resume cron <job id>`, commit + push (one-line message, ` (XX% complete)` as usual).
  5. End the loop: `ScheduleWakeup({stop: true})`. Final message, one line: `PAUSED until <resume_at>Z (<reading>)`.
- **While PAUSED**, any turn other than the resume prompt (a late worker notification, a stray cron) gets one line, `PAUSED until <resume_at>Z`, and no action. Exception: if the human types a message, answer it.
- **Resume.** The one-shot cron re-enters `/loop` with the §0 prompt. Step 0's usage check decides: GREEN → RUN (reconcile `[~]` per rule 3, then a normal iteration). Still ORANGE/RED (e.g. the weekly window is still high, or other sessions used the reset) → pause again right away with the new `resume_cron`, doing no other work.

**Commits (summary):** workers stage + validate (gate green); the coordinator is the only one who commits, merges, and pushes. **Every coordinator commit subject ends with ` (XX% complete)`**, an effort-weighted estimate of overall migration completion (human request 2026-10-11; keep it monotonic unless re-baselined in §2). It commits at every checkpoint and pushes `origin main` each time, so the remote always has a backup.

**Commit message format (coordinator):** one line, ending with ` (XX% complete)`: your estimate of overall migration completion, a whole number. Base it on §2's **Overall** line and update §2 first if the estimate changed. Examples: `B6: 40 move handlers verified (3% complete)`, `Checkpoint: wave 4 merged, §2/§9 updated (3% complete)`. Applies to every commit you make (merges, checkpoints, reverts); workers don't commit, so it doesn't apply to them.

**Model routing.** The Agent tool takes a per-call `model` (`haiku` | `sonnet` | `opus`), so the coordinator picks the model per spawn: `Agent({subagent_type: "general-purpose", isolation: "worktree", model: "<tier>", prompt: …})`. No per-model agent files are needed (the `spirited/.claude/agents/*.md` files pin `model:` in frontmatter for the game pipeline; that's the alternative, not required here). The coordinator itself runs on Opus.

Why tiers need rules: the Unicorn harness runs the original code and the Rust port on the same random inputs and compares memory + the stubbed-call log. It is not a byte-for-byte proof. A wrong port still passes when **inputs miss a branch** (rare event ID, edge value), when **stubs hide behaviour** (callees stubbed identically on both sides), or when **the porting agent weakens its own test** (narrower inputs, extra stubbing, re-recorded hash) — weaker models under "make it match" pressure do this more. So retry-until-match is only safe when **the harness isn't written or edited by the agent doing the port**; that's why Z9 (tool-generated stubs, per-function hashes) comes before cheap-model bulk work.

Rules that make Haiku safe:

1. **Escalation:** Haiku fails ~3 diff iterations (or returns BLOCKED) → re-spawn the item on Sonnet with the failure output. Sonnet fails twice → `[!]` for the coordinator (Opus) to handle or split.
2. **Hands off the tests:** porting workers may not touch `tools/rom-diff/*`, stubs, `check-*.sh`, or recorded hashes (other than via the check script). The coordinator rejects any porting branch whose staged diff touches them; harness changes come only from harness jobs and get coordinator review.
3. **Gate:** the gate must pass (clippy/fmt catch some quality issues, not faithfulness), and the coordinator re-runs the item's diff check on merged `main` (rule 6).
4. **Spot audit:** every ~20 Haiku merges, the coordinator (or a Sonnet job) reviews a random 2–3 ports against their pseudo-C for faithfulness the fuzzing could miss (rare branches); findings go to §8.

**Decide with data (pilot, right after Z8/Z9):** take ~20 B5 functions, same packets, run once with Haiku and once with Sonnet. Record tokens and wall-clock per **verified** function (not per call) in §9, and route leaf work to whichever is cheaper per verified function. Haiku is cheaper per call but may need enough extra iterations to lose on anything stateful. Re-check the choice every few waves.

**Definition of done (every item):** gate green; ported functions have `/// C:` comments; verified ones have a differential test (Rust test + `tools/rom-diff` mirror with matching hash) or hand-traced values; checklist/SYMBOLS synced; deviations documented.

## 5b. Independent validation (VALIDATION-AGENT; added 2026-10-12)

A second, read-only agent re-tests what lands on `main`: it re-runs the original code (Unicorn) and the Rust port on every commit batch, widens the inputs beyond the porter's 200 seeds, audits harness/spec edits, reads pseudo-C against the Rust for the classic port errors, and files findings. It exists because the per-function harness has blind spots (random inputs miss branches, stubs are guesses, call chains are never run end to end, and the porter runs its own check). Its prompt is self-contained: `$HOME/workplace/black/VALIDATION-AGENT.md`. It started at the 16% mark (baseline recorded in `validation/COMMITS.csv`); commits before the baseline are not reviewed.

**Separation of duties.** The validator never edits source, never commits, never touches this file. It writes only `validation/COMMITS.csv`, `validation/VALIDATION.md` (append), `validation/RUNS.md` (append) and `/tmp/blk/{wt,target,out}-validate`. The coordinator is the only agent that fixes code, and the only one that commits the `validation/` files (checkpoint, step 4). There is therefore nothing to merge and no conflict.

**Launch (coordinator).** After a merge batch is pushed (rule 6) and whenever `[TODO]`/unreviewed commits exist, if no validator is running and the usage mode is RUN:

```
Agent({subagent_type: "general-purpose", model: "sonnet", run_in_background: true, description: "validator run",
       prompt: "Read $HOME/workplace/black/VALIDATION-AGENT.md fully and run exactly one validator run (its §4). Batch hint: commits <oldest>..<tip> on origin/main (<one line on what landed>). Report in its §6 format."})
```

No `isolation: "worktree"` (it makes its own detached worktree at the exact tip). It counts as one worker slot (rule 7); one at a time. Measured cost (first run R-20261012-2027: 2 code commits, 15 areas): 11 min, ~150k Sonnet tokens. Don't launch it on docs-only pushes (checkpoints) — it would just mark them `SKIPPED`. In DRAIN/WRAP UP modes don't launch; a running validator is left to finish (it is cheap to lose: a killed run leaves `TODO` rows and re-runs next time).

**Import (coordinator, iteration step 2).** For each `- [TODO] V-NNNN — severity — area — fn — claim — commits — repro — fix notes — run` line in `validation/VALIDATION.md`:

- `high` → a fix job: add a `[ ] V-NNNN — PAR — <area>: <claim> — deps: none — notes: repro + fix notes from the finding` line under the owning phase in §6 (or attach it to the open item that owns the area), highest priority in its phase. The fix job's prompt tells the worker to **reproduce the finding on current `main` first** (it may be stale) and to run the finding's repro command, the area check and the dependent areas before reporting. If the finding says a test was weakened, the fix restores the test, never the other way round.
- `medium` → either a harness job (missing hint/stub/spec line) or an §8 note, by judgement; also a §6 line if it needs code.
- `low` → fold into the next harness job or fix it yourself in a checkpoint if it is a one-liner (stale generated file: re-run the script and commit).
- Not a bug (known deviation in §8, intended, or the validator misread) → `[REJECTED] — <one-line reason>`, so the next run doesn't re-file it.
  Then replace that line's `[TODO]` with `[IMPORTED]` (or `[REJECTED] — reason`), leaving the rest of the line untouched; commit the ledger at the next checkpoint. Nothing else in the file is edited by the coordinator; the validator only appends, so the two never collide (also: import only while no validator is running).

**Validator feedback.** Its final message has a "Harness notes for the coordinator" line (missing specs, flaky steps, commands that needed workarounds). Recurring items go into `VALIDATION-AGENT.md` §8 "Known pitfalls" (coordinator-owned edit, commit with the ledger). Fixes to the validator prompt itself are coordinator commits like any other.

### Asm reading notes

- `thumb_func_end` often sits at the first branch; a function runs to the next `func_start`.
- Thumb `add rX, pc` (hi-reg form) reads PC as instr+4, **unaligned**; `add pc, r0` jump tables branch to instr+4+offset.
- Much code is `.byte` blocks (e.g. 0x021D778C, handler code 0x021D85E8–~0x021E6xxx in battle_calc.s/battle_view_core.s); the decomp's file split there doesn't follow real source files.
- Runtime helpers: `FUN_0209C2B0` = `_u32_div_f` (returns dividend on /0, remainder in r1), `FUN_0209C0A4` = `_s32_div_f`, `FUN_0209C054` = `_ll_mul`, `FUN_0209B750` int→double, `0x0209B790` uint→double, `FUN_02082D44` = `MI_CpuCopy8(src,dst,n)`, `0x02082BCC` = `MI_CpuFill8`, `Heap_AllocDebug` = `0x02030734`, `Heap_Free` = `0x020307B0`.
- Debug filename strings in each file's `.data` identify the original source file (used for subsystem mapping).

### Verification methods

- Decompiled C: compile on host with shims; compare fuzz hashes.
- Asm only: `tools/rom-diff` runs original ARM9 + overlay code under Unicorn with Python stubs for unported callees; stateful code compared as whole memory images (e.g. 0x1F8-byte `BTL_POKEPARAM`) + log of stubbed calls; re-entrant callbacks via assembled Thumb stubs (`Emu.load_thumb`).
- UI rewrites (U-phase): side-by-side screenshot/timing comparison against the original running in an emulator (manual; human sign-off).
