## RE workflow: compute first, LLM last

**Principle:** tools do every step that can be computed (disassembly, decompilation, typing,
call graph, clustering, table extraction, harness setup, verification). The LLM does only the
semantic step that can't: turning one typed pseudo-C function into idiomatic Rust, and fixing
it when the differential test says it's wrong. The LLM should never read a raw `.s` file when
pseudo-C exists, and never more than one work packet at a time.

### Why the tools failed before (fixed 2026-10-11)

1. `main.elf` has all 182k decomp symbols (incl. ARM `$a`/`$t`/`$d` mapping symbols) but **zero-length sections**; the bytes exist only in `main.sbin` / `OVY_<n>.sbin`. Nothing could decompile it.
2. The decomp marks every `.byte`-encoded code block as `$d` (data), so the event handlers were invisible: Ghidra found **61 of 800** pool handlers in overlay 93.
3. rea needed Ghidra + JDK 21, which weren't installed.

`tools/re/mkelf.py` fixes 1 and 2: it writes a real ARM ELF (bytes + symbols) for one
co-resident overlay set, drops the `_@DummyFn`/`$b`/`$m` noise symbols, types every label that has a
mapping symbol as a function (Thumb bit set for `$t`), and seeds a `$t` + `sub_<addr>` function at
every odd word that points into loaded code (handler pools, callbacks). Result: **800/800** pool
handlers found. Ghidra, rizin, and rea all read this ELF with no extra config.

### Pipeline

| tier | step                                                                                                                                     | tool                                                                            | cost                                                                                 | output                                                                      |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |

| 0    | Group by shape (names + constants masked)                                                                                                | `clusters.py` (run by `decompile.sh`)                                           | 1 s                                                                                  | `clusters.txt`                                                              |
| 1    | Data, not code: getters/registries/pools → generated Rust tables                                                                         | script per table kind (Z11)                                                     | 0 LLM                                                                                | e.g. 518 getters `*out=N; return table` in overlay 93                       |

**Compounding:** every fact learned goes back into the tools, not just into Rust. A known
prototype → `tools/re/signatures.tsv` (re-run with `REUSE=1`; callers' decompilation improves at
once). Later: struct types from `black-rom/include/` and Rust ports → Ghidra data types (Z10), so
`*(short *)(p + 0x146)` becomes `mon->field`.

**Trust:** Ghidra output is a reading aid, never proof. Only the Unicorn diff (or hand-traced
values) marks a function verified (D2). Known Ghidra artifacts: `in_r3` / extra args from `push {r3, lr}`
(fix with a prototype), `Could not recover jumptable` on some veneers, "Unknown calling
convention" warnings on typed handlers (harmless).

### Commands

```sh
# once per machine: JDK 21 (mise install java@temurin-21.0.12+8.0.LTS) + Ghidra 12.1.4 unzipped to ~/tools
export BLACK_ROM_BUILD=$HOME/workplace/black/black-rom/build/black.us
T=$HOME/workplace/black/black-rust/tools/re
$T/decompile.sh battle main 93 94 95 96                     # first run ~2.5 min
REUSE=1 RANGE="021b6100 021f3b20" $T/decompile.sh battle    # after editing signatures.tsv, ~24 s
ls /tmp/blk/re/battle/pc | head; head -3 /tmp/blk/re/battle/clusters.txt
rizin -e scr.color=0 -qc 'aa; pdf @ 0x021df788' /tmp/blk/re/battle/battle.elf 2>/dev/null
rizin -e scr.color=0 -qc '/v4 0x021f1ea4' /tmp/blk/re/battle/battle.elf 2>/dev/null   # who loads this table
# rea (one-off): export GHIDRA_INSTALL_DIR=~/tools/ghidra_12.1.4_PUBLIC JAVA_HOME=<jdk above>
npx rea-agents decompile /tmp/blk/re/battle/battle.elf FUN_overlay_d_93__021d74f8 --provider ghidra --filter-output normalized_result
```

`mkelf.py` refuses overlay sets whose address ranges overlap (e.g. 93 and 90/98 share 0x021b6100);
pick the set that's loaded together at runtime. Sets in use: **battle = main 93 94 95 96**, **field = main 10 11 18 20 21**; the rest are proposed in `tools/re/sets.proposed.txt` / `OVERLAY-SETS.md` (Z12). `signatures.tsv` lines with overlay-RAM addresses (≥ 0x021542C0) and `@pool` lines are battle-only: `decompile.sh` filters them out for other sets. `$RE_OUT` defaults to `/tmp/blk/re` (ephemeral; regenerate, never commit).

### Measured (overlay 93, 2026-10-11)

Whole battle set (main + 93–96, no `RANGE`): **12,000 functions in 145 s** from scratch; 5,108 of
them in 747 shape clusters. Overlay 93 alone: 3,895 functions decompiled, 0 failures. Before seeding: 2,277 functions, 61/800 handlers.
`signatures.tsv` with the handler ABI on the 6 pools + 8 API prototypes applied 1,004 signatures.
Example: `021dcec4` (item registrar) decompiles to a clean 0xAC-entry loop calling
`021d6f0c(5, item, 6, …)`, matching what B4 found by hand-reading Thumb.
