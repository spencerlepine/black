# Overlay co-residency sets (Z12)

Generated by `tools/re/oversets.py` (inputs: ROM y9 overlay table, `main.elf` labels, overlay binaries). Proposed sets: `tools/re/sets.proposed.txt` (same format as `sets.txt`; the coordinator merges).

## Overlay load API (main)

- `0x02034AC4` `overlay_load(id)`: `FUN_02034BB0` first checks `[addr, addr+size)` of the new overlay against every loaded overlay in the same RAM region and panics (`FUN_02034714`) on overlap, then records `{id, 1}` in an 8-byte-slot table (slot count per region from `FUN_02034D08`) and calls `FS_LoadOverlay` (`FUN_02079264`).
- `0x02034A5C` `overlay_unload(id)`: finds the slot and calls `FS_UnloadOverlay` (`FUN_020792B8`).
- Call sites pass the id as `ldr r0,=id` / `movs r0,#id`. The loader's overlap check means **the set of loaded overlays is always non-overlapping**, and *M loads K* means M and K are resident together. `main` loads `10`+`11` at boot (`0x02005240`).

## How the sets were inferred

1. **Load sites** (strongest): every call to `overlay_load` with an immediate id; a module that loads K is co-resident with K.
2. **Address ranges** from y9: `[addr, addr+size+bss)`. 237 overlays share ~35 base addresses, so most are alternatives.
3. **Call edges**: Thumb/ARM `BL`/`BLX` targeting a labelled function of exactly one non-overlapping overlay (noisy; ranking only).
4. **Proc-table references**: literal-pool pointers to 3-word GFL_PROC tables in another overlay (who starts whom; not proof of co-residency).
5. **Layout parent**: base equals the end (incl. BSS) of exactly one overlay (`base = max(end(deps))` in the original linker script); bounds what may coexist but is not what is resident (e.g. every app is placed after the Wi-Fi base 9+13).
6. **Labels** from debug source-file strings in each overlay's data.

## Findings

- **Two base modes.** Normal: `main` loads **10 + 11** (`script_sys`/`scrcmd_*`/`fldmmdl` + `intrude_comm`). Wi-Fi: `main` loads 9 (+13/14/15/114). They overlap, so never together. 10+11 end at `0x02177020`; every app lives above it.
- **`field` = 10 + 11 + 18 + 20 + 21.** 10 loads 20 (`event_mapchange`); 21 loads 18 (`intrude_field`, 021881A6) early and unloads it at 02188B48; 21 and 10 call each other ~2,400 / ~250 times. Field children at base >= `0x021EE740` (gimmicks 36-65, 73-83, ...; 21 loads 29-35, 63, 74 plus table-driven ids) coexist with it.
- **The field overlay is unloaded for apps**: bag/party/summary/box/startmenu/pokedex all sit at 0x021B6100-0x021EE740 and overlap 21 (`0x02187F00-0x021EE740`).
- **Apps load `67` (ui-common) at their entry** (203, 204, 68, 72, 110, 120, 128, 135, 170, 171, 181, 207-210, 213, 214, 216, 218, 225, ...); `67` ends exactly at `0x021B95A0` where the 0x021B95A0 apps start.
- **Battle** (93) loads 94, 95, 96 and on demand 196, then 197 or 198; `10` and `11` load 93 as well, so they are resident during battle (`battle` in `sets.txt` omits them; add if battle code calls into 10/11). `tr_ai` 96 sits at 0x02187F00, overlapping 21: the field is unloaded during battle.
- 57 overlays are **32-byte stubs**; 69 more are network/Wi-Fi/union/C-Gear/IR/musical (see Not covered).
